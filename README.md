# 能楽の向こう側 / BEYOND NOHGAKU

日本の物語と土地を旅する — 能楽を入口に、歴史・土地・記憶をたどるデジタル文化誌。

Phase 1（指示書 27・35）の実装。コンテンツ量を増やす前に、
「大量の文化情報を、静かに・分かりやすく・回遊可能に見せられているか」を検証するための版。

## 動かす

```bash
npm install
npm run dev     # http://localhost:4321
npm run build
```

## 設計上の決定（なぜそうなっているか）

### 1. SOURCE LAYER をデータ型に埋め込んだ

史実と物語の混同を防ぐことがこのサイトの中心的な機能なので、
「どの層の情報か」を表示の都合ではなくデータの型として持たせている（`lib/types.ts` の `SourceLayerId`）。
旅程の各地点・年表の各行・本文の各段落が、それぞれ層を申告する。

数値化（史実度 ★★★）はしない。代わりに `同時代史料で確認` などの文言を出す。
色だけで層を区別せず、必ず英語ラベルと根拠の文言を併記し、罫線の種類も変える。

### 2. Journey Map は「日本のどこか」が分かる図にする

初版は海岸線を描かず番号だけを打っていたが、それでは縮尺も位置も読めず、
図としては記号の配置にしかならなかった。現在は次の三つを土台に置いている。

- 海岸線（Natural Earth 1:50m、パブリックドメイン）
- 経緯線と N/E の目盛り
- 100 km の縮尺

そのうえで、載せる情報を 地点 / 移動線 / 関連演目 に絞る。道路も鉄道も地形も描かない。

海岸線は実行時に地理データへ依存させたくないので、ビルド前に一度スクリプトで
SVG パスに変換して `content/japan-outline.ts` に置いている。

```bash
node scripts/gen-japan-outline.mjs
```

投影の設定は `content/map-config.json` をスクリプトと地図本体で共有する。
**設定を変えたら海岸線も生成し直すこと。**

地名の衝突は二つの方法で解いた。

- 本体は番号のみを打ち、地名は選択中の地点だけ大きく出す（いまの都道府県・市区町村を併記）
- 畿内は地名が数 px まで密集するため、拡大図（DETAIL）を日本海側の余白に置き、引出線でラベルを逃がす

平泉は旅程上に二度現れるため、同一座標の重複は出現順にずらして両方選べるようにしている。

モバイルでは番号が物理的に読めないので出さない。地図は位置の把握に徹し、
地点の選択は下の年表から行う（PC 版の単純縮小をしない、の具体的な意味）。

### 3. Comparative View はコンテナ幅で列数を変える

同じ部品が、記事の本文カラム（約 47rem）でもページ全幅（約 78rem）でも使われる。
ビューポートではなく「その部品が置かれた幅」で列数を決めたいので、
メディアクエリではなくコンテナクエリを使っている（`app/globals.css` の `.cmp`）。

- 〜42rem : 段組み
- 42rem〜 : 3 列（本文カラムの中。5 列は入らない）
- 60rem〜 : 媒体の数だけ列（全幅）

折り返した行の先頭に縦罫線が残らないよう、`:nth-child` で列位置を見て罫線を落としている。

### 4. 一覧は「分類して並べる」のをやめ、ファセットで絞る

分類ごとにベタで並べる方式は、件数が少ないうちしか成立しない。
200 曲になった時点で、読者は分類のなかを目で走査することになる。

そこで全 Entity を共通の軸でタグ付けし、`FacetBrowser` で絞り込む（`content/browse.ts`）。

| 対象 | 軸 |
| --- | --- |
| 演目 | 時代・地域・主題・人物・主役・形式・分類・特集・記事の有無 |
| 土地 | 地方・都道府県・土地の性格・特集・演目・記事の有無 |
| 人物 | 立場・時代・登場する曲・地域・記事の有無 |
| 横断 | 種別・時代・地域・主題・特集 |

- 同じ軸のなかは OR、異なる軸のあいだは AND
- 件数は「その軸以外の絞り込みを適用した状態」で数えるので、選んでも 0 件になる選択肢は最初から 0 と出る
- 軸の値が増えたら上位 8〜10 件だけ見せ、残りは「ほか N 件を見る」で開く
- 絞り込みの状態は URL に入る（`/ja/plays?theme=怨霊&era=源平の争乱`）。
  記事からも「同じ軸で、ほかの曲を探す」で戻れる

軸を足すときに触るのは Entity の型と `content/browse.ts` だけで、画面側は触らない。

### 5. 「いまのどこか」を必ず併記する

古い地名だけを並べると、読者は辞書や地図を片手に読むことになる。
`Place` は `modernName`（市区町村まで）と `access` を必須に近い情報として持ち、
地図の選択ラベル・年表の各行・記事のメタ表・一覧ページのすべてで併記される。

同じ理由で、人物の肩書きは「白拍子」ではなく
「白拍子。歌い舞う女性の芸能者で、義経に従った」と、それだけ読んで分かる文にしている。
それでも足りない言葉は `content/glossary.ts` に集め、
記事ごとに「この記事の言葉」として右のレールに出す（`components/GlossaryRail.tsx`）。

同じ理由で、一覧の既定のグルーピングは旧国名ではなく **現代の地方区分と都道府県** にした。
旧国名は副次情報として添える。`enLocation`（Kyoto, Kansai のような簡略表記）も持たせ、
将来の英語版と、いま読んでいる海外の読者の両方に備えている。

### 6. 特集は「タグの束」、地図はレイヤー

特集は、タグ付けされた記事を一貫した切り口でグルーピングしたもの。
したがって「どの特集に属するか」自体がひとつの軸になり、地図の上では重ねられるレイヤーになる。

`content/features.ts` がそのレジストリで、特集を足せば
土地の地図のレイヤー選択にも、演目・土地の絞り込み軸にも自動で現れる。

土地の地図は既定でどの旅程も引かず、全地点を点として置くだけにしてある。
旅程は選んだときだけ線で結ばれる（`components/PlacesMap.tsx`）。
特集が 10 本になっても、既定の画面は静かなままになる。

### 7. 記事は「問い」から始める（憲法 7・18）

あらすじ → 見どころ → まとめ、という順序にしない。記事の型は次のとおり。

```
TITLE / 問い / LEAD
01 ON STAGE      まず、能では何が起こるのか
02 EVIDENCE      歴史上は何が分かっているか
03 ORIGINS       原典ではどう描かれたか
04 WHAT CHANGED  能は何を変えたか
05 CONTEXT       当時の社会と信仰
06 READINGS      別の読み方
07 TODAY         現代から見ると何が面白いか
PLACE / ARCHIVE / SAKE / PERFORMANCE / RELATED / CONTINUE
```

この型の実証版が [橋弁慶](app/ja/plays/hashi-benkei/body.mdx)（約 4,100 字）。
船弁慶・安宅はまだ旧構成のままで、この型への書き直しが次の作業になる。

SOURCE LAYER が「どの史料に属するか」を示すのに対し、
`View` は「誰の読みか」を示す（研究上の解釈 / 異説 / 本サイトの考察）。
断定を避けるためではなく、読者が自分で判断できるようにするために分ける。

検索から来た読者のために、本文の前に **AT A GLANCE**（何が起きる曲か・舞台はいまのどこか・
時代・主役・形式・上演時間・公演件数）を置き、左のレールに目次を出す。
四千字の本文に直接落とさず、読むかどうかを先に決められるようにする。

### 8. 記事の終わりで迷子にしない

順番のある特集では、関連記事の一覧だけでは居場所が分からなくなる。
記事の末尾に全 13 章の目盛りと前後の章を置き（`components/FeatureNav.tsx`）、
左のレールには常に「第 02 章 / 全 13 章」を表示する。

### 9. PLACE は「行って何が見られるか」まで書く

土地の説明だけでは読んで終わってしまう。
`Place.sites`（歩いて見られるもの）と `Place.takeaway`（授かれるもの・持ち帰れるもの）を
データとして持ち、`PlaceGuide` が現地案内として描画する。

観光広告にはしないので、「なぜそれがそこにあるのか」を必ず添える。
たとえば安宅住吉神社の難関突破の御守は、能が作った関所の場面が
そのまま御利益の形になった例として載せている。

### 10. 記事は MDX、構造は TypeScript

本文の散文は MDX（`app/ja/plays/*/body.mdx`）。
章立て・レイヤー表示・比較表は MDX から直接使える部品として登録してある（`mdx-components.tsx`）。

一方、メタ情報・関係・史料・公演・アーカイブは構造化データ（`content/`）。
将来 CMS に移すときに、この境界がそのまま移行単位になる。

## 注意

- `content/performances.ts` は **UI 検証用のサンプル** で、実在の公演ではない。
  `PERFORMANCES_ARE_SAMPLE` を `false` にする前に、出典 URL と取得日時つきの実データへ差し替えること。
  画面上にもサンプルである旨を表示している。
- 写真・図版は未収録。`Fig` は「何の写真がそこに入るべきか」を明示したプレースホルダを出す。
- 英語版（`/en/`）は未実装。URL 構造と固有名詞のローマ字併記だけ先に用意してある。
- 史料に関する記述は、確認できる範囲を層として示す方針で書いている。
  個々の記述を公開する際は、出典の具体的な巻・条の照合を推奨する。
